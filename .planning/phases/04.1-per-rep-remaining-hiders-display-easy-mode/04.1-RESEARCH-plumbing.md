## 2. Recommended plumbing approach (work item 1)

### Recommendation: Option (b) — store `difficulty_easy` as a `GameController` attribute (`self._controller._easy_mode`)

Both options preserve the duck-typed dependency direction (no `game.py` import in `gui_game.py`). I recommend **option (b)** for minimality and precedent.

#### Option (a) — new `start_countdown` kwarg (REJECTED, but documented)
Add `easy_mode=True` kwarg to `start_countdown`; GameTab stores `self._easy_mode`.
- Requires 4 changes: signature (`gui_game.py:203`) + body (`gui_game.py:216` area) + 2 call-site changes (`__init__.py:124`, `__init__.py:484`).
- The 2 import-path call sites (`__init__.py:710`, `__init__.py:755`) would use the default.

Set `self._controller._easy_mode` in `_continue_after_large_demo_fetch` after construction. GameTab reads it via duck-typing with a defensive `getattr`.

- `_on_start` (line 124) AND the async-drain 'done' branch (line 484) BOTH go through `_continue_after_large_demo_fetch` where the controller is constructed at line 378. Setting `_easy_mode` right after line 378 covers BOTH fresh-game paths with **ONE** code change.

**Why option (b) matches codebase precedent:**
- `game.py:40` initializes `self._found_color = 'green'` (a display preference on the controller).

## 3. Required pure-layer change (REVISED per cross-scope finding)

### `registry.remaining_by_rep()` — NEW pure method (REQUIRED)

The earlier assumption ("no pure-layer change — `difficulty_easy` already exists in the pure layer") is **WRONG** for SC3. The cross-scope finding (confirmed by reading the code) is:

**`registry.counts_by_rep()` (registry.py:244-264) counts ALL records — NO status filter.** Verbatim:
```python
def counts_by_rep(self):
    out = {rep: 0 for rep in GAME_REPS}
    for r in self._records.values():
        if r.rep is None:
            continue
        out[r.rep] = out.get(r.rep, 0) + 1
    return out
```
It increments `out[r.rep]` for EVERY record regardless of `r.status`. So for a game with 3 found + 4 hidden spheres, `counts_by_rep()` returns `{'spheres': 7, ...}` — NOT the remaining 4.

**SC3 requires per-rep counts that SUM to the total remaining** (the `_remaining()` count in `game.py:113-116` filters `status == HIDER_STATUS_HIDDEN`). So a NEW method `remaining_by_rep()` is REQUIRED.

### Specification of `registry.remaining_by_rep()`

| Aspect | Value |
|--------|-------|
| Location | `biochemeleon/registry.py` (PURE — stdlib + `GAME_REPS` from `setup_state`; NO `from pymol`) |
| Signature | `def remaining_by_rep(self):` (mirrors `counts_by_rep`) |
| Returns | `{rep: count}` for every rep in `GAME_REPS` (zero-filled, same key order as `GAME_REPS`) |
| Filter | `r.status == HIDER_STATUS_HIDDEN` (the ONLY difference from `counts_by_rep`) |
| `rep=None` handling | SKIP (same as `counts_by_rep` — post-`.pse` reload ghosts; `HiderRecord` with `rep=None` from `reconstruct_from_sentinels`) |
| Purity | YES — no `from pymol`, no Qt. WSL-unit-testable. |
| TDD candidate | YES — pure method, deterministic, small. Write the test first in `tests/test_registry.py` (or `tests/test_setup_state.py` pattern — stub `pymol` + `pymol.Qt` via `sys.modules` before import). |

### Reference implementation sketch (for the planner — NOT for the executor to copy verbatim)

```python
def remaining_by_rep(self):
    """Return {rep: count} for HIDDEN records, keyed by GAME_REPS.

    Mirrors counts_by_rep but filters status == HIDER_STATUS_HIDDEN so the
    per-rep counts SUM to the total remaining (SC3). Skips rep=None records
    (same as counts_by_rep). Zero-fills reps with no hidden hiders.
    """
    out = {rep: 0 for rep in GAME_REPS}
    for r in self._records.values():
        if r.rep is None:
            continue
        if r.status == HIDER_STATUS_HIDDEN:
            out[r.rep] = out.get(r.rep, 0) + 1
    return out
```

### Impact on Phase 4.1 scope

Phase 4.1 has **BOTH** a pure-layer change AND a Qt+cmd change:
1. **Pure-layer (registry.py)**: add `remaining_by_rep()` + unit test. WSL-runnable TDD.
2. **Qt+cmd plumbing (__init__.py)**: set `self._controller._easy_mode` after construction (1 line).
3. **Qt+cmd callback/label (gui_game.py)**: extend `_update_remaining` to read `counts_by_rep`/`remaining_by_rep` + format per-rep when `_easy_mode` is True (OTHER researcher's scope).

The pure-layer change is a TDD candidate that can be done FIRST (RED test → GREEN impl → REFACTOR), independently of the Qt plumbing.

## 4. Risk notes

### Risk 1: Countdown-vs-play timing — `_easy_mode` must persist across the 3-2-1 countdown
`start_countdown` (gui_game.py:203) sets `self._controller` then calls `_countdown_step(3)` which chains `QTimer.singleShot` for 3 seconds before `_begin_play`. The `_easy_mode` attribute is set on the controller in `_continue_after_large_demo_fetch` (BEFORE `start_countdown` is called), so it persists on the controller across the countdown. When `_begin_play` fires (after 3s) and eventually `_update_remaining` is called (line 256), `self._controller._easy_mode` is still set. **No risk** — the attribute lives on the controller, not on a transient countdown variable. (This is actually a STRENGTH of option (b) over option (a): option (a) would store `self._easy_mode` on the GameTab in `start_countdown`, which also persists across the countdown — both options are safe here.)

### Risk 2: `_begin_play` does NOT read `_easy_mode` today
`_begin_play` (gui_game.py:235-256) calls `self._update_remaining(self._controller._remaining())` at line 256. Today `_update_remaining` reads only the int `remaining` param. The OTHER researcher's callback change will either:
- (a) extend `_update_remaining` to also read `self._controller._easy_mode` + `self._controller.registry.remaining_by_rep()` (or `counts_by_rep`), OR
- (b) change the callback signature to pass `counts_by_rep` data.
Either way, `_begin_play`'s line 256 call may need updating (other researcher's scope). The plumbing (setting `_easy_mode` on the controller) is independent and can land first.

### Risk 3: `rep=None` in live games — should not occur, but `remaining_by_rep` defends
In a FRESH game (the only path Phase 4.1's SC tests — "at game Start"), `register()` always passes a valid rep (`HiderRecord.__init__` at registry.py:111-112 raises `ValueError` if `rep is not None and rep not in GAME_REPS`). So `rep=None` records only arise from `reconstruct_from_sentinels` (post-`.pse` reload). In a live game, `remaining_by_rep` will never skip a record for `rep=None` — the per-rep breakdown will always be complete. The `rep=None` skip is defensive for the reload/import path (out of scope for Phase 4.1).

### Risk 4: Imported games (out of scope) — `getattr` default `False` → total-only
`_on_import` (__init__.py:698) constructs `self._controller = game.GameController(target_obj)` but Phase 4.1 does NOT set `_easy_mode` there. The `getattr(self._controller, '_easy_mode', False)` defensive read returns `False` → imported games show total-only (hard mode). This is acceptable for Phase 4.1 (SC only mentions "at game Start"), but the planner should note it as a deferred gap: if imported games should also support per-rep display, a follow-up must set `_easy_mode` from the `.bcm` sidecar in `_on_import` (the sidecar stores the setup state via `persistence.build_bcm_dict`).

### Risk 5: `_on_cleanup` resets the label to `"Remaining: -"` (total-only format)
`__init__.py:786` — `self.game_tab._remaining_label.setText("Remaining: -")`. This is the cleanup reset. After Phase 4.1, if the label format changes (other researcher's scope), this reset string may also need updating to match. The plumbing change itself does NOT touch this line.

### Risk 6: `_on_restart_imported` reuses the import controller (no new `_easy_mode`)
`_on_restart_imported` (__init__.py:728-755) does NOT construct a new controller — it reuses `self._controller` from the import. So `_easy_mode` (if it was never set on the import controller) stays absent → `getattr` returns `False` → total-only. Consistent with Risk 4.
