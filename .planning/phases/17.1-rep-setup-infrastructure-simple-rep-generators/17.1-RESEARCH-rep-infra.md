## Executive Summary

Phase 17.1 turns the Phase-16 single-tier (VDW) game into an N-tier, per-rep dispatched game with lock-scene vs randomize distribution. The plumbing research produced **five decisive, probe-verified findings**:

1. **`mol repname` names FOLLOW the rep across `delrep` renumbering and are MONOTONIC — they are never reset by `backup::apply` or a full clear** (probe2). After `mol delrep 1` of {rep0:Lines, rep1:VDW, rep2:Licorice, rep3:Points}, the remaining reps are `0:rep0:Lines 1:rep2:Licorice 2:rep3:Points` — the Licorice rep kept its name at its NEW index; the deleted name resolves to `-1`. New reps continue the counter (rep4, rep5…), and after a full clear + re-add the names are rep5/rep6, after `backup::apply` rep7/rep8. **Consequence:** "track by stable name" works exactly as ROADMAP SC4 wants, but only for names captured AFTER `backup::apply` — a name captured before apply is dead. The pattern is: add game reps after apply → immediately `mol repname` each → store NAMES → resolve `mol repindex` (guard `-1`) at use time.

2. **All 10 GAME_REPS style spellings read back from `molinfo` byte-identical to the GAME_REPS list** (probe1), so style→tier mapping is the identity map. Non-GAME_REPS styles (Ribbons, Bonds, HBonds, Beads, QuickSurf, Isosurface, VolumeSlice) also read back verbatim and are correctly excluded by the existing `lsearch -exact` filter. **But an INVALID style string errors ("Unknown atom representation command") and silently falls back to Lines** (probe4: Nonbonded/Dot/Off → readback `<Lines>`) — a failed-style rep becomes indistinguishable from a real Lines rep in detection. Always `catch` around `mol modstyle` and validate style strings against GAME_REPS.

3. **The game's own hider reps ARE re-detected as scene reps by style-only detection, and the sentinel-selection filter defeats this** (probe1). On a molecule carrying the 2 game reps (style VDW, selections `resname GAM and beta < 0 and user2 < 1|> 0`), `get_active_reps` returns `Lines VDW VDW`. Filtering per-index `{style sel}` pairs by `string first {resname GAM} $sel >= 0` excludes them exactly (selection read-back is byte-exact). **Recommended structural fix:** derive lock-scene per_rep from `backup::snapshot`'s already-captured rep list INSIDE `start_game` (after the active-game guard, on the clean restored original) — game reps structurally cannot be present there; keep the sentinel filter as defense-in-depth.

4. **`user3` (and `user4`) exist in VMD 1.9.3 and are the clean per-atom tier channel** (probe1/probe2/probe4). Settable on multi-atom selections with a numeric scalar (broadcast); selectable with exact match (`user3 1`) and comparisons (`user3 > 0`); read-back is FLOAT (1.0); real atoms default 0. The combined conjunction `resname GAM and beta < 0 and user2 < 1 and user3 1` is valid selection syntax and was accepted as a rep selection via `mol modselect` (read-back byte-identical). The per-tier partition math verified exactly: 5 hiders split tier1={3 atoms}, tier2={2}, one tier-1 find → tier1 hidden=2/found=1, tier2 hidden=2/found=0. This enables **one hidden/found rep PAIR per active tier (2N reps) with static, unchanged-string selections** — the existing modselect re-assert contract generalizes unchanged. (`user` is written by tag_sentinels but never read anywhere in vmd/; `user2` = found flag; `user3` is free.)

5. **`registry::reconstruct_from_sentinels` is single-rep and destructive-on-recall — the registry needs one new pure API for multi-tier rep stamping** (probe1 P17D: a second call CLEARED the first tier's records; count=2 after two calls). Add e.g. `registry::set_rep {idx rep}` / a bulk `assign_reps` — pure, TDD'd in `test_registry.test`.

**Primary recommendation:** Keep `backup.tcl`/`mutation.tcl` untouched. Extend `game.tcl::start_game` to `start_game {molid hider_count {per_rep {}} {lock_scene 0}}` (backward compatible), derive lock-scene tiers from the snapshot via a new PURE module (`rep_tiers.tcl`: scene-reps→per_rep mapping, per_rep∩detected filtering, empty→`randomize_per_rep(hider_count, detected-or-GAME_REPS)`), stamp `user3` tier codes in-place (new mol-bridge proc), and generalize `hiders.tcl` to add one hidden/found pair per active tier with name-keyed tracking. The registry gains one pure per-record rep setter. No pick_bridge, backup, or GUI changes are required by the plumbing.

## RQ1 — Lock-scene detection (molinfo per-rep introspection)

### 1.1 The verified introspection forms

- **Enumerate:** `set n [molinfo $mol get numreps]` then loop `i` in `0..n-1` (backup.tcl:43-48 pattern).
- **Per-rep read:** the COMBINED-BRACES form ONLY —
  `[molinfo $mol get "{rep $i} {selection $i} {color $i} {material $i}"]` returning `{style sel color material}` (backup.tcl:46, demos.tcl:94). The single-field form `molinfo get {rep $i}` **fails with `molinfo: incorrect format for 'get'`** — re-verified by accident in probe1 (my delrep dump loop used it and aborted; Pitfall 3 stands).
- **Style read-back is the IDENTITY map to GAME_REPS** — VERIFIED for all 10 (probe1, 1xdn + 11 reps): requested `Lines/VDW/Licorice/CPK/Cartoon/NewCartoon/Trace/Tube/Points/DynamicBonds` → read back `<Lines>` `<VDW>` `<Licorice>` `<CPK>` `<Cartoon>` `<NewCartoon>` `<Trace>` `<Tube>` `<Points>` `<DynamicBonds>`. No normalization table needed.
- **Selection read-back is byte-exact** — a rep whose selection was set via `mol modselect $i $m {resname GAM and beta < 0 and user2 < 1}` reads back `resname GAM and beta < 0 and user2 < 1` verbatim (probe1 game-reps section). This makes selection-text filtering reliable.
- **A fresh molecule has `numreps=1`, style `<Lines>`** (1znf, 1k8p, 1xdn all VERIFIED) → lock-scene on an untouched demo detects `{Lines}`.

### 1.2 What to do with non-GAME_REPS reps

- Valid non-GAME_REPS styles read back verbatim and are skipped by the existing `lsearch -exact $GAME_REPS $style` filter (demos.tcl:95): VERIFIED for `Ribbons, Bonds, HBonds, Beads, QuickSurf, Isosurface, VolumeSlice` (probe4).
- **Invalid style names (including common assumptions like `Nonbonded`, `Dot`, `Off`) print `ERROR) Unknown atom representation command '<X>'` and the rep silently becomes `<Lines>`** (probe4). Consequences: (a) never trust a style string not in GAME_REPS — always `catch` `mol modstyle`; (b) a rep whose style command failed is DETECTED as Lines — an accepted, minor detection blind spot (the user would have had to type an invalid style).
- Volumetric styles load but spew render errors in text mode (`draw_volslice: no texture map has been generated!`, probe4) — reconfirms surface/volumetric reps as anti-features (SC1 exclusion stands).

### 1.3 Duplicates: `get_active_reps` does NOT dedup

`get_active_reps` appends one entry PER REP INDEX whose style is in GAME_REPS (demos.tcl:93-99). VERIFIED: two VDW reps → `... VDW ... VDW` (probe1). The v1 semantic (CITED `gui_setup.py:398-408 _sync_reps_from_scene`) is a **presence boolean per rep** (`checked = rep in active`), so the lock-scene derivation must **dedup** — either fix `get_active_reps` to dedup or dedup in the new pure mapper. Recommend the pure mapper dedups and `get_active_reps` gains the same behavior (or is superseded by it).

### 1.4 Game reps must not be re-detected — placement + filter

- **VERIFIED false positive:** on a molecule with the game's 2 hider reps added (style VDW + sentinel selections), `get_active_reps` → `Lines VDW VDW` (probe1).
- **VERIFIED filter:** build per-index `{style sel}` pairs; skip any pair where `[string first {resname GAM} $sel] >= 0`; then apply the GAME_REPS filter. Result on the game molecule: `{Lines}` — correct (probe1).
- **Structural placement (recommended):** run detection INSIDE `start_game`, from `backup::snapshot`'s rep list (step 1, which already captures `{style sel color material}` per rep — backup.tcl:39-50), i.e. AFTER the active-game guard has cleaned any prior round. The restored/loaded original can carry at most the user's own scene reps, so game-rep contamination is structurally impossible; the sentinel filter stays as defense-in-depth (it also covers the pathological case of a user manually loading `biochemeleon_game.pdb`).
- `demos::get_active_reps` remains useful for GUI feedback (checkbox sync), but the GAME-AUTHORITATIVE derivation should be the snapshot-based pure mapper.

### 1.5 v1 lock-scene semantics (CITED — design intent)

`pymol/biochemeleon/gui_setup.py:372-408`: toggling lock-scene ON calls `_sync_reps_from_scene(obj)` → `get_active_reps` → **checks the per-rep checkboxes for detected reps and DISABLES them (locked)**; spinboxes stay EDITABLE for checked reps (counts remain user-controlled); toggling OFF re-enables all checkboxes. Detection is presence-based, not count-based. Also synced on target change while lock-scene is checked (`gui_setup.py:351-352`).

## RQ2 — Rep tracking by stable name (`mol repname`/`mol repindex`)

All VERIFIED in probe2 (1k8p + 4 reps):

| Operation | Result |
|---|---|
| `mol repname $m 0` on a fresh molecule | `rep0` (default Lines rep is named) |
| Add reps via form B | names continue `rep1, rep2, …` by creation order |
| `mol delrep 1` (middle) | remaining reps KEEP their names at shifted indices: `0:rep0 1:rep2 2:rep3` |
| `mol repindex $m rep2` after the delrep | `1` (name→current index) |
| `mol repindex $m rep1` (deleted) | `-1` — **no error; the clean guard** |
| `mol repindex $m rep99` (unknown) | `-1` |
| `mol repname $m 99` (out of range) | **ERROR** `mol repname: invalid repid 99` — index args must be guarded/range-checked |
| Add a new rep after a delrep | gets `rep4` — **the name counter is MONOTONIC, names are never reused** |
| Full clear (`delrep 0` loop) + add 2 | names `rep5`, `rep6` — **NOT re-derived from rep0** |
| `backup::apply` (clear + re-add snapshot reps) | names `rep7`, `rep8` — **apply does NOT reset the name counter** |

### 2.2 The name-keyed flow (what to store where)

- **Registry records** already store the TIER name (GAME_REPS string: `VDW`, `Lines`, …) in each record's `rep` field (registry.tcl:16-19) — that is the name-keyed flow's data plane and needs no shape change (only the new per-record setter, §RQ3.4).
- **VMD rep identity for the game's own reps** (hiders.tcl's `hidden_rep`/`found_rep` cached INDICES): generalize to a namespace dict `{tier_code → {hidden_name found_name}}` captured via `mol repname` immediately after the reps are added (post-apply), plus the tier's style. At use time resolve `mol repindex $m $name`; **`-1` ⇒ rep gone → error "hider reps not added"** (generalizes hiders.tcl:107-111's existing numreps guard). Indices must never be cached across any rep mutation (Pitfall 9, clonerep.tcl:92-96).
- **`molinfo get numreps` updates immediately after `mol addrep`** (probe1/probe3: `base = numreps` then addrep+modstyle loops behaved exactly as hiders.tcl:76-92 does today).

## RQ3 — `game.tcl::start_game` per-rep dispatch

### 3.1 Current shape and the backward-compatible extension

Current: `start_game {molid hider_count}` (game.tcl:91), game_state dict `{game_molid hider_count snapshot}` (FROZEN per 15-05, game.tcl:37-41), step order: guard → snapshot → make_placeholder_hiders → mutate → backup::apply → `hiders::add_hider_reps` → registry DI reconstruct (game.tcl:137-165).

Recommended extension (minimal, backward compatible — existing 2-arg call sites keep working):

```tcl
proc ::biochemeleon::game::start_game {molid hider_count {per_rep {}} {lock_scene 0}} {
```

- `per_rep` = the validated dict from setup_state (only GAME_REPS keys, sum ≤ hider_count — validate_state already guarantees this, setup_state.tcl:171-189).
- After the guard + snapshot (steps 1), if `lock_scene`: derive `detected` from `$snapshot`'s reps via the pure mapper (§RQ1.4); **filter `per_rep` keys to `detected`** (drop counts on non-scene reps); if the filtered dict is empty → `per_rep = [randomize_per_rep $hider_count $detected]` (reuses quick-008's non-empty-subset guarantee, setup_state.tcl:204-225 — the DI `game_reps` parameter makes the lock-restriction a one-argument change).
- If NOT lock_scene and `per_rep` empty → `per_rep = [randomize_per_rep $hider_count $GAME_REPS]` (quick-008 default, now inside start_game so the console path and the GUI path both get it).
- game_state gains `per_rep` (additive key; the "FROZEN" shape is deliberately extended — update the doc comment and any smoke that asserts the exact key set).

### 3.2 The per-rep loop lives in game.tcl (composition root)

v1 precedent (CITED): `_prepare_and_start` built `(payload, rep)` specs and `GameController.start` looped `mutation.insert_hider_for_rep` per spec, registering `rep=rep` (`__init__.py:364-374, 466-502`; `game.py:48-90`). v2 equivalent: game.tcl owns the tier loop:

1. Derive an ordered ACTIVE-TIER table from `per_rep` (GAME_REPS order for determinism): `{tier_code style count}` where tier_code = 1-based ordinal of the tier **within this round's active list** (the code is only a discriminator; the registry's `rep` field carries the GAME_REPS name).
2. For each tier: call the placement fn (Phase 16's `make_placeholder_hiders` for VDW; the new Lines/Licorice generators for those tiers) with the tier's count; **concatenate the record lists in tier order**.
3. ONE `mutation::mutate` call with all records (molid changes once).
4. `backup::apply $snapshot $game_molid` (unchanged).
5. NEW `hiders::add_hider_reps $game_molid $tier_specs` (§RQ4) — after apply, before registry reconstruct (ordering constraint preserved, game.tcl:145-147).
6. NEW: stamp `user3` tier codes in-place (mol-bridge proc, §RQ4.3) using the tier→indices map.
7. `registry::reconstruct_from_sentinels` with the EXISTING DI lambda (game.tcl:154-159 — `[list apply {lambda} $game_molid]`, NEVER bare `[apply ...]`), then the NEW registry per-record rep stamping from the tier→indices map.
8. game_state `{game_molid hider_count snapshot per_rep}` with **`hider_count` = the EFFECTIVE total (sum of per_rep values)** — see Pitfall P9.

The tier→indices map is derivable WITHOUT extra molinfo calls: `fetch_hider_indices` returns indices in file order == record order (probe3: `555 556 557 558 559` for 5 records appended in order), so splitting the sorted index list by the tiers' cumulative counts is exact (probe3 did precisely this). Records within a tier may be reordered only if a tier's generator does not preserve record order in the file — each generator must preserve its record order (a generator contract to state in the plan).

### 3.3 Under-generation (v1 parity, CITED)

v1 caps per tier at what the geometry allows and warns non-blockingly (`__init__.py:472-473` `min(count, len(neighbor_ids))`, `__init__.py:495-508` `_gen_warnings`). v2 plumbing must tolerate a tier producing fewer records than requested: registry count = actual records; the tier's rep pair still selects whatever exists (an empty selection is harmless). The effective-total rule (P9) applies.

### 3.4 Registry multi-tier gap — CONFIRMED, one new pure API

`reconstruct_from_sentinels` does `set _records [dict create]` (clear) then stamps ONE rep for ALL records (registry.tcl:38-45). VERIFIED in VMD (probe1 P17D): two back-to-back calls → only the second tier's records survive. **Needed:** a pure per-record/bulk rep API, e.g.:

```tcl
proc ::biochemeleon::registry::set_rep {idx rep} { ... }          ;# error if idx unregistered
proc ::biochemeleon::registry::assign_reps {mapping} { ... }      ;# dict idx -> rep
```

TDD in `vmd/tests/test_registry.test` (the DI/harness pattern is established there). Alternative considered and rejected: calling reconstruct once per tier with tier-filtered fetch lambdas — impossible without changing reconstruct's clear-first semantics.

### 3.5 What does NOT change

- `pick_bridge` (delivers the index only; game.tcl resolves tier from the registry record).
- `backup.tcl` snapshot/apply/restore (§RQ5).
- `mutation.tcl` mutate/tag_sentinels/write_combined_pdb (the tier stamping is a separate in-place step; `user` ordinal and `user2` found flag semantics untouched).
- The DI shape and the "never bare `[apply ...]`" rule.

## RQ4 — `hiders.tcl` generalization: N tiers, hidden/found per tier

### 4.1 One pair per tier — REQUIRED, not optional

VMD colors/styles per-REP (hiders.tcl:15-17) — there is no per-atom style override. A Lines-tier hider must render in a Lines rep to blend; a shared single hidden rep would render every tier as VDW. So: **one hidden rep + one found rep per ACTIVE tier (2N reps)**, style = the tier's GAME_REPS style:

- hidden tier-t: `mol modstyle $i $m <style>`; `mol modcolor $i $m Element` (blending color choice is the sibling research's domain; plumbing-verified that modcolor accepts `Element` and reads back `Element`, probe1/probe3); `mol modselect $i $m {resname GAM and beta < 0 and user2 < 1 and user3 <t>}`
- found tier-t: same style; `mol modcolor $i $m ColorID 7`; `mol modselect $i $m {resname GAM and beta < 0 and user2 > 0 and user3 <t>}`

VERIFIED end-to-end on 2 tiers (probe3): reps added post-apply at base..base+3 with monotonic names rep2..rep5; the combined selection strings accepted; read-back byte-identical (`resname GAM and beta < 0 and user2 < 1 and user3 1`). Partition math VERIFIED standalone (probe4 §(1)).

**Never-hide rule is structurally satisfied:** the found rep of tier-t contains only found hiders of tier-t (`user2 > 0`), the hidden rep keeps unfound ones visible — neither rep is ever hidden (`mol showrep off` is never issued), so the pickability contract (AGENTS.md: hidden reps cannot be picked) is preserved by construction. Double-count prevention stays the caller-side registry-status guard (game.tcl on_pick), unchanged.

### 4.2 Name-keyed bookkeeping

`add_hider_reps {molid}` → `add_hider_reps {molid tier_specs}` where tier_specs = ordered `{tier_code style}` list. It returns/records `{tier_code → {hidden_name found_name}}` (via `mol repname` immediately after each addrep — names are stable thereafter, §RQ2) plus the styles. `mark_found_visual {molid idx}` keeps its signature: set `user2 1` on the picked index, then re-assert **ALL pairs'** `modselect` with the UNCHANGED literal strings, resolving indices via `mol repindex` per call with the `-1` guard (≤ 20 modselects at the 50-hider cap; idempotent, same cost class as today's 2). Re-asserting ALL pairs (vs only the picked hider's tier) avoids a tier lookup in hiders.tcl and keeps the unchanged-string contract trivially — recommended.

The existing "hider reps not added" error (hiders.tcl:110) generalizes to the `-1`/missing-name case.

### 4.3 Tier-code stamping (mol-bridge)

A small new proc (hiders.tcl or mutation.tcl — planner's call; recommend hiders.tcl to keep mutation.tcl's PDB-rebuild scope clean, or mutation.tcl next to tag_sentinels since it is also a post-load in-place field set):

```tcl
proc stamp_tier_codes {molid tier_of} {   ;# tier_of: dict tier_code -> index list
    dict for {code idxs} $tier_of {
        set sel [atomselect $molid "index $idxs"]
        $sel set user3 $code     ;# NUMERIC only -- non-numeric errors (probe3)
        $sel delete
    }
}
```

- `$sel set user3 <num>` broadcasts over the multi-atom selection (VERIFIED probe2: 3-atom selection, exact-match select `user3 1` → 3).
- Codes are 1-based ints (0 = "untagged"; real atoms default 0 — probe1). The sentinel conjunct `resname GAM and beta < 0` scopes every selector anyway.
- Read-back is FLOAT (`1.0`) — compare numerically only (same discipline as user2, hiders.tcl:112-113).
- Stamping happens AFTER mutate (fields do not survive PDB rebuild) and BEFORE/with registry reconstruction; the tier→indices map comes from the dispatch order (§RQ3.2).

## RQ5 — `backup.tcl` interplay (ordering + restore)

VERIFIED (probe3 full flow + probe2 name semantics):

- **Ordering:** snapshot (pre-mutate) → mutate (mol delete + mol new; the new molecule has only its default rep) → `backup::apply` (clear + re-add scene reps; numreps returns to the snapshot count — probe3: snapshot 1 rep → post-apply numreps 1) → **game tier reps added AFTER apply** (base = numreps, deterministic; names monotonic and stable for the round). This is exactly the Phase-16 SS5.5 ordering, generalized from 2 reps to 2N.
- **Cleanup removes all game reps for free:** `backup::restore` does `mol delete $game_molid` + `mol new original` + apply — the 2N game reps live on the deleted game molecule (probe3: restored molid, 555 atoms, numreps=1). No new cleanup code.
- **Restart / active-game guard:** unchanged semantics — the guard's cleanup restores the original BEFORE the new round's snapshot, so snapshot-based lock-scene detection always sees clean scene reps (§RQ1.4).
- **No repname assumption survives apply for PRE-apply reps** (§RQ2): anything the game tracks by name must capture names after apply. Nothing in the current game does otherwise (hiders.tcl captures base/indices after apply today).
- `backup::snapshot` fidelity for exotic styles VERIFIED (probe4: Ribbons/Bonds/QuickSurf/… round-trip through apply verbatim).

## PITFALLS discovered (Phase 17.1-specific)

**P1 — repnames never reset; pre-apply names are dead.** The name counter is monotonic per molecule; `backup::apply`/full-clear do NOT restart it at rep0 (probe2: rep5/rep6 after clear+add, rep7/rep8 after apply). A name captured before apply belongs to a deleted rep. → Capture game-rep names ONLY after adding them post-apply; resolve via `repindex` at use time.

**P2 — `repindex` returns -1 (no error) for unknown/deleted names; `repname` ERRORS on out-of-range index** (`mol repname: invalid repid 99`, probe2). → Guard: check `-1` after every repindex; never call repname with an unvalidated index.

**P3 — invalid style → ERROR + silent fallback to Lines.** `mol modstyle` with a unknown style prints `ERROR) Unknown atom representation command 'X'` and the rep becomes `<Lines>` (probe4: Nonbonded/Dot/Off). A failed-style rep is indistinguishable from a real Lines rep in lock-scene detection. → `catch` every `mol modstyle`; only ever pass GAME_REPS strings as styles.
